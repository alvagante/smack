# Security, performance, implementation and design review since v0.6.0

Review date: 2026-10-31. Baseline: `34367fb` (v0.6.0). Committed head: `38f683c`.
Scope includes all three commits after the baseline and the pre-existing staged installed-apps work. Review fixes are unstaged; original staged changes were preserved.

## Result

The six original bounded improvements and both P1 remediations are implemented. Subprocess cleanup now has an enforced deadline; network sampling has an independent visible-only cadence. All four P2 findings are now remediated as described below; representative workload profiling remains outstanding. No confirmed new privilege bypass or shell injection was found in the inspected paths. This is source review with regression tests and focused resource measurements, not a security certification or a full application energy profile.

## Implemented fixes

1. **Bound stderr memory.** `Sources/Smack/CommandRunner.swift` previously read stderr to EOF without a limit, defeating every new collector's output cap. Both streams now drain continuously while retaining at most `outputLimit` bytes per stream. Either stream can mark the result truncated. Two real subprocess regression tests cover simultaneous output above pipe capacity and stderr-only truncation. The limit is per stream, so raw retained bytes can reach twice the configured limit, before String and parser allocations.
2. **Respect filesystem cancellation.** Agent, runtime, home-browser and installed-app discovery now propagate caller cancellation into their detached workers. Scan loops check cancellation between filesystem operations. App-size workers stop scheduling further measurements when cancelled. Already-blocking filesystem or metadata calls remain non-interruptible; view-created unstructured refresh tasks can still outlive the view.
3. **Reduce runtime discovery probes.** Runtime bin candidates are normalized, deduplicated and checked for directory existence before probing executable names. Project scans stop probing children when their directory budget is exhausted. This removes repeated PATH/standard-location work and probes of missing bin directories without changing the supported runtime inventory.
4. **Reduce directory-preview CPU.** Long listings reuse one DateFormatter and cache owner/group names per listing, rather than constructing a formatter and repeating account lookups for every entry. Existing listing, permissions, special-file and preview tests still pass.
5. **Prevent alias-only uninstall.** Discovery prefers actual bundles over symbolic-link aliases when deduplicating. Alias-only entries remain visible but cannot be uninstalled: recycling the alias would otherwise leave its target installed while claiming its full size was removed. Tests now require the actual bundle and cover an alias whose target is outside discovery roots.
6. **Recheck running apps during uninstall.** Each Trash operation checks the current running-app set. A later selected application that starts while an earlier Trash operation awaits completion is skipped. A regression test simulates this transition. This narrows the race; checking state and recycling a bundle are not an atomic operation.

## P1 remediation (implemented)

### Resolved P1: subprocess timeout does not guarantee completion

Original defect: CommandRunner sent SIGTERM once and then blocked on pipes/process exit. SIGTERM-resistant children, descendants holding inherited pipes and blocked stdin writes could defeat timeout or cancellation. Three regression tests reproduced this, taking about 2.08 seconds despite a 0.1-second deadline/cancellation and failing a 1.5-second completion bound.

Implemented in `Sources/SmackIPC/Subprocess.swift`, shared by CommandRunner and the helper:

- `posix_spawn` creates a separate process group atomically. Explicit argv/environment and file actions preserve the no-shell execution boundary. Descriptors above stderr and close-on-exec rules prevent descriptor aliasing/leakage.
- A single worker polls nonblocking stdin/stdout/stderr. Each output stream retains only its byte budget while continuing to drain; stdin never blocks another worker.
- Monotonic deadlines and task cancellation send SIGTERM to the owned group, escalate to SIGKILL after 250 ms and stop pipe cleanup after 500 ms (plus scheduling/poll latency). A parent that exits while descendants hold pipes gets a 250 ms drain grace, then the same cleanup policy.
- `waitid(WNOWAIT)` keeps the leader's PID reserved until all group signals have been sent, preventing a late cleanup signal from targeting a reused process group. The leader is then reaped. If the kernel has not delivered exit by the cleanup deadline, a separate waiter reaps it later without retaining pipes or captured output.
- Read-only commands honor cancellation. Explicit `cancellable: false` mutations still finish when their caller disappears; their intentionally unbounded operation duration is unchanged. Actual exit status and output are preserved.

The three previously failing regressions now complete in about 0.4 seconds. Additional tests cover cancellation before launch, output caps on both streams, stdin delivery, nonzero exit status and mutation completion despite caller cancellation.

`Sources/SmackHelper/FileActivityCapture.swift` now uses the same runner. Normal captures still request five seconds from fs_usage; an independent seven-second watchdog bounds a stuck tool, followed by the bounded termination grace. Each XPC connection owns its capture task. Interruption/invalidation cancels that task and the global single-capture gate is released on completion. PID/start-time validation and the 1 MiB returned-output cap remain in force. The helper compiles; no root installation or live privileged trace was performed.

Boundary: process groups contain ordinary descendants, not programs deliberately escaping into a different session/group. Such programs can no longer hang the caller through inherited pipes, but this is not a sandbox or a guarantee to terminate escaped processes. A kernel-stalled process may retain the separate reap waiter until the kernel permits exit; it does not retain the caller or pipe buffers.

### Resolved P1: continuous nettop sampling is expensive

Original defect: every process snapshot launched nettop, creating nearly continuous sampling at the visible one-second process cadence and extra work during background/history collection.

`ProcessNetworkSampler` now owns one five-second start-to-start loop, enabled only while the panel is visible. `CollectionScheduler` forwards visibility through the process provider contract. ProcessSnapshotService reads the latest completed observation without launching or awaiting nettop, so process sampling is independent of network probe latency. Hidden/background and scheduled-inventory snapshots cause no network launches.

Hiding cancels and awaits the existing probe, clears cached values and stops the loop. Rapid hide/reopen waits for teardown before launching another probe. Generation checks discard late replies. A failed probe publishes unavailable data rather than zero; successful cached values expire after ten seconds using monotonic receipt time. The original sample timestamp still guards PID/start-time reuse. The first visible rate is unavailable until the initial probe completes; thereafter rates refresh every five seconds. README and the application-chart footnote document that cadence. Network throughput remains live-only and adds no history persistence.

A focused harness compiled the actual Subprocess and ProcessNetworkSampler sources, using the exact production nettop arguments wrapped in `/usr/bin/time -l`:

| Run | Observation window | nettop launches | Child user + system CPU |
| --- | --- | --- | --- |
| Previous per-snapshot cadence | about 10 seconds | 10 | 13.62 seconds |
| New visible provider | 9.9 seconds | 2 | 2.70 seconds |
| Following hidden interval | 1 second | 0 additional | 0 additional |

This is about 80% less sampler CPU in these short runs, consistent with 80% fewer launches. It measures child CPU, not full-app CPU, kernel-wide impact or a sustained energy average. Each nettop invocation is still expensive; a persistent sampler could reduce startup cost further, but continuous one-second spawning and hidden-panel sampling have been removed. No new disk persistence was introduced. Memory remains bounded by one in-flight command, one latest sample and the existing parser/output limits.

Tests verify one shared loop across repeated visibility/read requests, zero hidden collection calls, five-second sleep budgeting, stale-value expiration, failure invalidation and the distinction between unavailable data and measured zero.

## P2 remediation (implemented)

### Resolved P2: synchronous Accessibility discovery can block the UI

`Sources/Smack/NativeMenuBarStore.swift`, `refresh`, calls `HostedMenuBarDiscovery.items` on MainActor every two seconds. `NativeMenuBarAccessibility.swift` makes multiple remote AX calls per item. A per-message timeout does not bound total discovery latency. An unresponsive host can therefore stall the panel for seconds.

Implemented: a dedicated serial utility queue performs hosted AX discovery with a 750 ms monotonic budget. Every attribute request uses the remaining budget, capped at 100 ms; window and action requests are also bounded. Expired discovery returns no snapshot, preserving last-good images. Coalescing covers discovery and capture together. Visibility, feature and display generations reject obsolete discoveries and captures. Regression coverage suspends an injected host, proves MainActor responsiveness and single-flight discovery, changes the display before completion, and checks zero-budget refusal. This is cooperative budgeting around synchronous system calls, not hard preemption of an OS call.

### Resolved P2: installed-app sizing causes eager disk walks

`Sources/Smack/InstalledAppsMonitor.swift`, `setVisible`, `refresh`, `measure`: opening Summary can trigger size measurement for every application after the five-minute inventory cache expires. Spotlight misses fall back to four concurrent recursive bundle walks, potentially including Xcode. This generates metadata I/O and CPU even when the user only wants system metrics. The UI also publishes each measured size separately.

Implemented: Summary and inventory refresh perform discovery only. Measure sizes is an explicit detail-page action. Successful results cache for five minutes using path, inode, modification time and size of bundle/Contents/Info.plist metadata; refresh invalidates changed entries. One utility worker measures sequentially and publishes one batch. Spotlight misses walk at most 100,000 entries or two seconds per bundle, checking cancellation between entries. Enumeration/metadata errors, budget exhaustion and cancellation never publish a partial byte total as complete. Failed measurements are labeled Incomplete and remain retryable. View tasks are structured; panel hiding cancels discovery and sizing workers even when initiated by a view. Tests cover cheap discovery, cached reuse, metadata invalidation, cancellation and entry/time refusal. Nested in-place changes that leave bundle metadata untouched can remain cached until the five-minute expiry; already-blocking filesystem/Spotlight calls cannot be preempted. No representative large-bundle benchmark was run.

### Resolved P2: aggregate memory budgets are missing

`Sources/Smack/DevEnvironmentMonitor.swift`, `inspections`, retains all inspected environments until discovery refresh. Discovery permits 512 installations and each can retain several reports with up to one million bytes per stream per command. Per-command caps did not bound total cache retention. Implemented: a 16 MB aggregate UTF-8 payload budget, least-recently-used eviction and refusal of a single oversized inspection. Only one inspection runs at a time. Tests verify eviction order and oversized refusal. The budget measures retained text, not exact allocator overhead.

`Sources/Smack/Views/ApplicationIcon.swift`, `ApplicationIconCache`, retains icons indefinitely by identifier/path. Installed-app browsing expands this pre-existing pattern. Implemented: NSCache has a 256-entry/16 MiB cost limit and retains only 64-point thumbnails. Cache keys include exact bundle path, bundle metadata identity and a five-minute expiry interval. Exact-path lookups take precedence over bundle identifiers; changed bundle metadata produces a fresh key. NSCache limits are advisory eviction thresholds, not a hard process RSS cap.

`Sources/Smack/UserHomeMonitor.swift` materializes and sorts every directory entry before limiting long-listing output to 5,000. The regular browser listing has no entry limit. Binary plist decoding and XML serialization allocate before the decoded-size check. Implemented: opendir/readdir retains at most 5,000 names with a one-second enumeration budget before sorting; metadata rendering also has a one-second budget. Both browser and long listings label partial results. Binary plists are conservatively refused before decoding; XML remains bounded text and is never parsed or reserialized. Tests cover bounded enumeration, binary refusal and existing text/XML behavior. Individual filesystem calls remain non-interruptible.

### Resolved P2: expensive detailed collections share one refresh cycle

`Sources/Smack/DockerMonitor.swift` refreshes details every 15 seconds while the page is active, collecting stats, disk usage, images, volumes and networks regardless of the selected section. `docker system df` may make the daemon perform significant work. Homebrew detail collection also performs a full Cellar `du` when details refresh.

Implemented: Docker status remains on its 15-second cycle. Statistics run only for Containers; selected images/volumes/networks refresh at most once a minute automatically. Storage runs only on section selection or explicit Refresh, with a five-minute selection cache. Cache identity includes CLI path, DOCKER_HOST, DOCKER_CONTEXT and Docker config modification time; context changes during collection discard results. Homebrew services and cleanup/Cellar sizing load only for their selected sections, cache for five minutes, and never run during automatic Summary refresh. Source changes and mutations invalidate details. Providers serialize reads/inspections and mutations: mutations wait for Docker reads; Brew blocks conflicting requests. Mocked tests cover section command counts, periodic suppression of storage, unavailable remote/stopped daemons, and a 10,000-container inventory in batches of at most 100. Conservative existing per-command deadlines remain unchanged. No live large-inventory/remote-context benchmark or real Docker/Brew mutation was performed, so the cadence values are provisional workload policies, not measured daemon-performance guarantees.

## Security and privacy boundaries

- New helper tracing retains administrator and same-signer XPC authorization checks. PID and start time are checked before and after capture; output is capped; executable and arguments are fixed. No new client-supplied shell expression was introduced.
- Commands use explicit argument arrays. Docker actions use stable container IDs and option terminators. Automatic Docker collection requests selected fields instead of environment secrets; full inspection is an explicit user action.
- Home previews use nonblocking open plus fstat to reject FIFOs/devices and read at most 1 MiB plus one byte. Text and plist previews, Docker inspect, logs and crash filenames can still expose local credentials/private data through the intentional copy/reveal UI. They should remain ephemeral and excluded from telemetry and persistence.
- Runtime inspection executes discovered local programs with the user's privileges. Avoid treating arbitrary custom-folder executables or inherited runtime startup hooks as trusted merely because their names match a runtime. Any stronger guarantee requires an explicit probe execution policy.
- Installed-app protection is partly discovered state. Revalidate protection and filesystem identity immediately before destructive operations if uninstall grows beyond moving user-selected bundles to Trash. Running-state checks alone cannot provide an atomic guarantee against launches or path replacement.
- Live network throughput adds no history columns or new network-history persistence. Existing history retention and pruning remain in force. Read-only collectors primarily consume CPU, memory and metadata I/O; Brew operations can download, install and remove files by design. The resource table measures only the sampled nettop process, not daemon work, page-cache effects or all application writes.

## Standards

No additional documented coding-standard breach was confirmed. Existing provider injection and MainActor publication patterns were preserved. Possible divergent change: MonitorStore now owns navigation, metrics/history and every feature model. Possible duplicated lifecycle code: each monitor independently implements visibility, freshness, loading and cancellation. These are design heuristics, not mandatory violations. Define shared collection policies before extracting a scheduler abstraction; avoid a broad rewrite of working feature models.

## Spec

No issue-tracker configuration or independent originating issue/spec was available; strict spec compliance review is therefore skipped. README feature promises and existing tests were used as the behavioral baseline. Confirmed mismatches fixed here: bounded command output was incomplete, app uninstall could remove only an alias, and later-started apps could bypass the batch running-state check. Normal traces request five seconds; a helper-owned seven-second watchdog now bounds failures independently of the external tool, followed by up to 500 ms of process cleanup.
